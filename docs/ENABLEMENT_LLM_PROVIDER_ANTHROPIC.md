# Enablement — `LLM_PROVIDER=anthropic` (Claude setup-token backend)

**Status (2026-07-29):** built, tested, flag default **OFF** (`LLM_PROVIDER=openai`). Live behavior UNCHANGED until an operator flips the flag. **Not yet proven against a live Claude conversation** — see "What is not proven" below.

## What it does

Lets the agent run on Anthropic Claude instead of OpenAI, authenticating with either credential shape:

| Credential | Generated by | Billed against |
|---|---|---|
| `sk-ant-oat…` — **setup token** | `claude setup-token` | your Claude **Pro/Max subscription** |
| `sk-ant-api…` — API key | console.anthropic.com | API credits |

The code never asks which one it has: `anthropic_service._auth_headers` branches on the prefix. Swapping one for the other in `.env` needs no code change.

Approach ported from the Car_App Android project (`ge.carapp.data.ai.AnthropicDirectClient`), where it runs in production.

## Where it plugs in

Every LLM call in this codebase funnels through exactly two functions, so the provider decision lives in one place and nothing downstream changed:

```
openai_service._chat_completion   ──┐
openai_service.chat_with_tools    ──┤
                                    ▼
                          LLM_PROVIDER switch
                            ├── "openai"    → unchanged OpenAI path
                            └── "anthropic" → anthropic_service
                                               ├── Bearer / x-api-key auto-detect
                                               ├── billing attribution → system prompt
                                               ├── messages + tools translation
                                               └── OpenAI-shaped dict back out
```

`parent_llm_engine`, `adult_llm_engine`, `parent_reply_composer`, `parent_turn_analyzer` and every test mock are **untouched**. They read responses through duck-typed accessors (`_first_choice` / `_choice_message` / `_tool_calls` / `_message_content`) that already accept plain dicts, so `anthropic_service.to_openai_response` returning a dict is enough.

## The three details that actually break

1. **Billing attribution lives in the SYSTEM PROMPT, not in a header.** Despite the name, `x-anthropic-billing-header: cc_version=…; cc_entrypoint=cli; cch=00000;` is prepended as the first line of `system`. Without it a setup token reaches **Haiku only** — Sonnet and Opus return 400. It is applied on every call path (completion, tool call, connection test); a test covers each one, because missing it on one path fails only that path.

2. **Clipboard round-trips corrupt tokens.** Zero-width and non-breaking spaces make the auth header invalid and Anthropic answers 401 with a message that never mentions whitespace. `sanitize_token` strips everything outside printable ASCII. It cannot fix a token wrapped across two lines in `.env` — keep it on one line, unquoted.

3. **Anthropic's message rules are stricter than OpenAI's.** `split_messages` hoists mid-conversation `system` turns (this project appends a reasoning directive as one) into the top-level system string, merges consecutive same-role turns, guarantees the first turn is `user` (this bot greets first, so histories legitimately open with an assistant turn), and drops empty blocks.

## Flag-OFF guarantee (the default)

With `LLM_PROVIDER=openai`, `_use_anthropic()` returns `False` on its first line and the Anthropic branch is never entered — behavior is identical to before this patch.

A provider of `anthropic` with an empty `ANTHROPIC_AUTH_TOKEN` is treated as a config mistake, not a reason to drop live traffic: it logs once at ERROR and serves the turn from OpenAI.

## Boot requirements follow the provider

`OPENAI_API_KEY` used to be an unconditional entry in `REQUIRED_VARIABLES`. Removing it from the Railway dashboard after adding the Claude variables crash-looped the container at import time, before any LLM call could run:

```
app.config.ConfigurationError: Missing required variables in .env: OPENAI_API_KEY
```

The requirement is now provider-aware (`_required_variable_groups`):

| `LLM_PROVIDER` | LLM credential required at boot | `OPENAI_API_KEY` |
|---|---|---|
| `openai` (default) | `OPENAI_API_KEY` | required — unchanged |
| `anthropic` | `ANTHROPIC_AUTH_TOKEN` **or** `ANTHROPIC_API_KEY` | optional |

Under `anthropic` with no OpenAI key, `ANTHROPIC_FALLBACK_TO_OPENAI` **auto-disables** — leaving it nominally on would mean every retry fails against an unconfigured client. The boot log line reports the resolved state:

```
[openai] model=… token_param=… llm_provider=anthropic openai_key=unset anthropic_fallback=False
```

Keeping `OPENAI_API_KEY` set alongside the Claude token is the safer deploy: Claude serves traffic and OpenAI stays available as the fallback.

## How to enable (operator)

1. Generate a token: `claude setup-token` (requires an active Claude Pro/Max subscription).
2. Put it in `.env` — or the Railway dashboard — on one line, unquoted. Either variable name works: `ANTHROPIC_AUTH_TOKEN=sk-ant-oat…` or `ANTHROPIC_API_KEY=…`.
3. Verify credential **and** model together — a valid token can still 400 on the configured model:
   ```
   python -m tools.check_anthropic_token          # plain completion
   python -m tools.check_anthropic_token --tools  # + tool-call round trip
   ```
4. Only once both pass: set `LLM_PROVIDER=anthropic` and restart (settings are `@lru_cache`d).

`ANTHROPIC_FALLBACK_TO_OPENAI=true` (default) retries a failed Anthropic call on OpenAI so a provider outage cannot cost a lead. Set it `false` while debugging so Claude errors surface instead of being masked.

## Rollback

Set `LLM_PROVIDER=openai` (or remove the line) + restart. No data migration, no state to unwind.

## What is proven

* `tests/test_anthropic_setup_token_2026_07_29.py` — 45 tests: prefix-based auth selection, token sanitization, billing attribution on all three call paths, message/tool/response translation, tool-call round-trip through the **real** `parent_llm_engine` accessors, provider switch, fallback on/off, that the token never appears in an error message, and the boot-requirement matrix above (including the exact Railway crash configuration).
* Full suite after the change: **5535 passed, 1 failed, 28 skipped**. The single failure — `test_approved_copy_service_2026_07_11.py::test_parent_flow_start_book_intent_uses_fast_track_and_advances_state` — is **pre-existing**, verified by re-running it with these changes stashed.
* The wiring reaches Anthropic for real: `tools/check_anthropic_token` against the token currently in `.env` returned `OAuth access token has been revoked` — a credential-specific answer from the API, which means the request shape and auth header were accepted as far as token validation.

## What is NOT proven

* **No live Claude conversation has been run.** The token in `.env` is revoked, so neither the plain-completion nor the tool-calling path has completed end-to-end against the real API. Regenerate the token and run `--tools` before enabling.
* **No quality comparison.** Whether Claude's Georgian sales replies match or beat the current `gpt-4.1-mini` output for this prompt set is unmeasured. The prompts, sanitizers and guardrails were all tuned against OpenAI. Treat enablement as a behavior change requiring the same live-review discipline as any other capability flag.
* **Token-cap semantics differ.** `max_tokens` is a hard cap on Anthropic and truncation looks like a short reply, not an error. The values here (200–500) were chosen for OpenAI; watch for clipped replies on first live use.

## Caveat worth knowing

`cc_entrypoint=cli` in the billing attribution presents the request as coming from the Claude Code CLI. The token is yours and the app is yours, but Anthropic can change or block this at any time — which is exactly why `ANTHROPIC_FALLBACK_TO_OPENAI` defaults to `true` and the `x-api-key` path is kept working. A classic API key needs no attribution and is unaffected.
